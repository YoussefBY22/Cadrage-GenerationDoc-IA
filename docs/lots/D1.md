# Lot D1 — Circuit de validation, comptes, versions, audit

## Fait
- `app/auth/` : mots de passe argon2 ; jetons opaques (`secrets.token_urlsafe`), stockés hachés (SHA-256) dans `sessions`, expiration `session_ttl_hours`.
- `api/deps.py` : mode `dev` conservé ; mode `token` (Bearer → 401 sinon). `config.py` : défaut `auth_mode="token"` (seule ligne touchée).
- `app/workflow/` : `state_machine` (pure : table des transitions, motif, quatre yeux, échecs non acquittés, sections complètes), `versions` (accès livrables/versions/commentaires/audit, re-vérification via `repo.get_chunks`), `diffing` (difflib par section et par phrase).
- Routes : `routes_auth` (login, logout, me, `POST /dossiers/{id}/members`), `routes_deliverables` (GET, versions, PUT content, restore, diff, commentaires), `routes_workflow` (transitions, acquittements), `routes_audit`.
- Édition d'un livrable `approved` → nouvelle version « edited » + retour à `draft` (audité) ; `in_review`/`rejected` : 409 `NOT_EDITABLE`.

## Testé
`cd backend && ruff check . && pytest -q` → `All checks passed!` ; `296 passed, 1 skipped` (Postgres). Nouveaux : 40 (table 16 transitions, quatre yeux, acquittement journalisé, 401, 404 inter-dossiers sur 11 routes, audit par action, mot de passe et jeton jamais en clair, diff/restauration).

## Limites
- Pas de route de création de comptes ni de réinitialisation : les comptes se créent via `repo.create_user` (script d'admin à prévoir).
- Acquittement stocké dans `audit_log` (action `sentence.acknowledge`, par version) : pas de table dédiée.
- Re-vérification : pas de `generation_runs` enregistré pour une édition manuelle.

## Écarts aux contrats de 06
- Routes ajoutées : `POST /deliverables/{id}/acknowledgements` `{section_key, sentence_index (-1 = refus)}`, `GET /deliverables/{id}/comments`. `GET /deliverables/{id}` renvoie aussi `reports` (rapport + tpv par section).
- Réponses 401 du mode token : format FastAPI `{"detail": …}` (pas `{"error": …}`).
- « Rôle reviewer/admin » = rôle de membre du dossier ∈ {reviewer, admin} **ou** rôle global admin.

## Demandes
- B1 : le `Repository` n'expose ni sessions, ni lecture de livrable/versions/commentaires/audit ; D1 lit via `repo.engine` et `storage.schema`. À intégrer au Protocol si souhaité.
- Les tests des autres lots utilisent la fixture `client` (mode dev forcé) ; tout nouveau test sans elle doit fixer `AUTH_MODE` (défaut désormais `token`).

## Pour comprendre
Le circuit de validation est un relais à deux témoins : l'auteur ne peut pas signer son propre travail, et le relecteur ne signe que si chaque phrase douteuse a été regardée et initialée (acquittement). Chaque passage de témoin est consigné dans un registre qu'on ne peut qu'allonger (audit).

## 3 questions
1. Pourquoi stocker le SHA-256 du jeton plutôt que le jeton ?
2. Pourquoi renvoyer 404 et non 403 pour un livrable d'un autre dossier ?
3. Que devient l'approbation si on modifie un livrable approuvé ?

## Notions pour le glossaire
- Quatre yeux : l'approbateur doit être une autre personne que l'auteur.
- Acquittement : décision explicite d'un relecteur d'accepter une phrase en échec ou un refus.
- Jeton opaque : chaîne aléatoire sans contenu lisible, seule son empreinte est conservée.
