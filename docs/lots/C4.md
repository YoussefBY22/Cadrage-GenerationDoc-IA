# Lot C4 — Orchestration de la génération « preuve d'abord »

## Fait
- `app/services/generation.py` : flux 06 §7 (`generate_section`), création de ToR/CdC (`create_deliverable`, contexte = initiative choisie), `call_model` (1 nouvel essai si `LLMError`, erreur rappelée dans le prompt), traces `record_run/retrieval/verification`, version `generated`, audit. Refus **sans appel** si passages < `min_sources`.
- `app/services/findings.py` : passages par document en lots de 8 → `LLMFindings` → chaque constat vérifié comme phrase `fact` ; seuls les constats sans problème bloquant sont enregistrés (les autres reviennent dans `rejected` avec leur rapport) ; doublons ignorés ; `patch_finding` (correction re-vérifiée, validation refusée si bloquant).
- `app/services/roadmap_service.py` : constats validés → `LLMInitiatives` → `Initiative` (F→id, dépendances par titre→id, sources P→chunk) → `scoring` + `graph` ; `patch` recalcule sans modèle (scores, durées, dépendances, cycles signalés).
- Routes : `routes_findings.py` (`findings:extract`, `GET findings`, `PATCH /findings/{id}`), `routes_generation.py` (`roadmap:generate`, `PATCH /deliverables/{id}/roadmap`, `POST /dossiers/{id}/deliverables`, `sections/{key}:generate`). Dossier ou objet étranger → 404.

## Testé
`cd backend && ruff check . && pytest -q` → `All checks passed!` ; `269 passed, 1 skipped` (Postgres). Nouveaux : 8 tests services (honnête TPV 1 ; tricheur : UNKNOWN_SOURCE/NUMBER_NOT_FOUND/FACT_WITHOUT_SOURCE enregistrés ; invalide puis valide → attempts=2 ; deux échecs → `invalid` ; refus → 0 appel ; feuille de route + recalcul + cycle ; constat tricheur rejeté), 4 tests API, 1 e2e (corpus B4 institution 1 → constats → validation → feuille de route → ToR de l'initiative n°1, 6 sections, TPV 1, runs en base) : 1,4 s.

## Limites
- Le « modèle honnête » des tests recopie des phrases : il valide la chaîne, pas la qualité d'un vrai modèle.
- Ré-extraction : ajoute les constats nouveaux (pas de suppression ; la `Repository` n'a pas de `delete_finding`).
- Lectures `deliverables`/`findings`/`documents` par `repo.engine` (comme B5) : la `Repository` ne les expose pas.
- `min_sources` compte les passages renvoyés, pas les passages cités.

## Écarts aux contrats de 06
- Le contexte « initiative choisie » d'un ToR/CdC est conservé dans la version initiale sous `DeliverableContent.roadmap` (un `RoadmapResult` à 1 initiative) : aucun champ ajouté au contrat.
- `findings:extract` renvoie `{findings (avec rapport), rejected, runs}`  ; `POST …/deliverables` refuse le type `roadmap` (422) : la feuille de route est créée par `roadmap:generate`.
- Génération/PATCH roadmap exigent l'état `draft` (409 sinon).

## Demandes
- D1 : l'acquittement d'une phrase `failed` et la re-vérification sur `PUT content` peuvent réutiliser `verify_section` ; prévoir `Repository.get_deliverable`.
- B1 : `get_deliverable(id)`, `list_deliverables(dossier_id)` et `delete_finding` simplifieraient ces services.

## Pour comprendre
Le code est un contrôleur de chantier : le modèle (l'artisan) propose, mais chaque phrase est mesurée contre les pièces du dossier avant d'être posée. Pas de pièce, pas de travail : on ne l'appelle même pas. Un mur douteux n'est pas démoli, il est marqué pour l'inspecteur.

## 3 questions
1. Pourquoi refuser avant l'appel au modèle plutôt qu'après ?
2. Pourquoi un constat à problème bloquant n'est-il pas enregistré, alors qu'une phrase de section l'est ?
3. Que se passe-t-il si les dépendances proposées forment un cycle ?
